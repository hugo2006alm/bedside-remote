## Published signing and runtime evidence

[v0.1.1-alpha.1](https://github.com/hugo2006alm/bedside-remote/releases/tag/v0.1.1-alpha.1) was published by [a fully successful pipeline](https://github.com/hugo2006alm/bedside-remote/actions/runs/39112985683). Its manifest records Android and Mozilla signing as complete, Windows Authenticode as missing, and physical acceptance as incomplete. All eight published asset digests match the release checksum file; downloaded APK, XPI, source and metadata hashes were also checked. This remains a development prerelease.

[v0.1.2-alpha.1](https://github.com/hugo2006alm/bedside-remote/releases/tag/v0.1.2-alpha.1) subsequently passed [all pipeline jobs](https://github.com/hugo2006alm/bedside-remote/actions/runs/39116512169), including the Android distribution smoke test and publication. It adds native disconnect diagnostics and channel metadata normalization; the text-delivery changes described below were developed after that release.

[v0.1.3-alpha.1](https://github.com/hugo2006alm/bedside-remote/releases/tag/v0.1.3-alpha.1), source commit `893eb28b4ed41d371c2ac88b3ad525f8507e6d25`, passed [all pipeline jobs](https://github.com/hugo2006alm/bedside-remote/actions/runs/39118164625). All nine published assets match GitHub's SHA-256 digests; the eight entries in `SHA256SUMS.txt` match their downloaded files. The APK matches the pinned persistent signing certificate, and the signed XPI identifies version 0.1.3 with the expected add-on ID. Windows Authenticode and full physical acceptance remain incomplete.

The exact published 0.1.3 Windows setup and Android APK were installed over the earlier versions on the development PC and physical phone. Android reports version code 10 and version name `0.1.3-alpha.1`; Windows reports the same release and source commit. Android reconnected securely without pairing again, and the normal Zen instance launched the updated installed Native Messaging executable. The user then updated the signed extension in Zen; Android displayed the current YouTube title and the channel `Ben Morris` once, without the previously observed duplication.

[v0.1.4-alpha.1](https://github.com/hugo2006alm/bedside-remote/releases/tag/v0.1.4-alpha.1), source commit `537f1c0170543021e256d7eb8592b2913538daf0`, passed [all pipeline jobs](https://github.com/hugo2006alm/bedside-remote/actions/runs/39129805874), including Compose tests and the exact signed distribution APK smoke test. All nine published asset digests and all eight checksum entries were verified after publication. The downloaded APK matches the pinned persistent certificate, and the 0.1.4 XPI has the expected identity and verified signature. The installed Windows setup and APK are byte-for-byte the corresponding published assets; their physical discovery and preserved-pairing results are recorded below. The user's working Zen extension remains 0.1.3. Windows Authenticode and full physical acceptance remain incomplete, so the release stays alpha.

The released Windows installer was also installed on the development PC. The running installed agent served protocol v1 over TLS pinned to its stored certificate and rejected a valid unauthenticated WebSocket handshake with HTTP 401. This test sent no desktop input.

Physical testing on 2026-10-18 used a Nothing A059P running Android 17 (API 37) and the exact signed v0.1.1-alpha.1 APK. Installation, manual LAN pairing with the agent certificate fingerprint and temporary code, explicit approval on Windows, secure connection, and automatic reconnection after force-stop/relaunch passed. Reinstalling the same signed APK preserved pairing and reconnected; version-to-version upgrade was subsequently checked with 0.1.3 above. Light/dark appearance was checked and restored to dark.

Automatic LAN discovery initially showed no nearby PC. Android's NSD diagnostics later confirmed successful discovery/resolution with the Tailscale CGNAT address before the usable Wi-Fi address. The old single-host selection rejected the first address and discarded the service. The correction selects an allowed address on the phone's subnet from all modern NSD results or bounded Windows TXT hints for legacy NSD. Three Android regression tests cover mixed adapters, address rejection, IPv6 and subnet prefixes; two Windows checks cover safe, bounded TXT hints. After installing the CI-built 0.1.4 Windows setup and signed APK (version code 11), the physical phone displayed the PC and its correct Wi-Fi endpoint under Nearby computers. Its existing pairing reconnected securely and YouTube metadata continued through the user's 0.1.3 Zen extension. No desktop input was sent during this discovery test. Legacy Android discovery selection is covered by regression tests, not a physical pre-Android-14 device.

Zen 1.23.3b (Gecko 158.0) initially reported `No such native application com.bedside.remote`. Registry and native-host probes passed from the agent's tooling context, including a temporary headless Zen profile, but did not establish the user's normal browser connection. Running `./scripts/repair-browser-integration.ps1` in the user's ordinary PowerShell reported `Registration matched before repair: False`; after repair, the user confirmed the extension popup showed connected. Process inspection then confirmed the normal Zen instance launched the registered host with the expected manifest path and add-on ID. The precise reason the two execution contexts observed different registration states has not been established.

On the same physical Android device, the signed 0.1.1 extension relayed the open YouTube video's title, thumbnail, duration and changing progress. A contextual pause changed the control to Play and held progress at 1:05 across separate observations; resuming restored Pause and progress subsequently advanced to 1:37. This validates that live Android/Windows/Zen control path, not the remaining streaming checklist. Duplicated channel labels observed in that version were corrected and physically checked after the 0.1.3 extension update described above. Windows UI automation was unavailable because its runtime failed to initialize.

The physical queue test started empty: appending a pasted official YouTube link created one entry in Android and the Windows `queue.json`, without selecting it for playback. After force-stop/relaunch and secure reconnection, Android displayed the saved entry again. Removing that entry restored both Android and the persisted queue to empty. Reordering, play-now/play-next navigation, natural-end advancement, and sharing from the official YouTube app remain pending. No AndroidRuntime error was present for the running application process after this test.

Physical text input initially corrupted `Bedside Remote - café, ç 😀` in Windows Notepad 11.2607.14.0: rapid Unicode packets repeated isolated low-surrogate units, and a first pacing-only candidate still failed. The final local Windows candidate uses layout keystrokes plus paced UTF-16 fallback; the user confirmed the exact phrase, including both accents and the emoji, in a fresh Notepad document. Tests used the signed Android 0.1.1 APK and preserved pairing across agent restarts. This correction and the longer Android text acknowledgement timeout are included in the installed 0.1.3 release; the short Notepad test preceded that packaged upgrade. Other editors, keyboard layouts and maximum-length physical text remain unverified.

## Physical acceptance checklist

The observations above are partial physical evidence. The following checklist remains open until all relevant cases are executed and recorded with device/browser versions:

- Extend the recorded matching-key APK/Windows upgrade and signed-extension checks to a separate clean Windows installation; verify other persisted settings and queue data.
- Pair across the LAN with the displayed fingerprint, code and explicit Windows approval; reject incorrect fingerprint/code; verify reconnect, manual connection, discovery, revocation of an active client and firewall private-network behavior.
- Test D-pad, Unicode including Portuguese accents, gestures/scroll, native keyboard/IME behavior, media/volume and normal desktop applications. Confirm behavior at Windows integrity boundaries.
- Share official YouTube links from Android; play now/next/append; reorder/remove/clear; observe natural-end advancement once, manual video changes, multiple tabs, refresh/close, autoplay denial and network loss.
- Extend the recorded live Zen YouTube checks to the remaining playback/control cases. Validate Netflix playback, episode/intro/recap/audio/subtitle actions when available in the user's Zen installation, recording unsupported DRM explicitly. Do not require the user to switch to Firefox or bypass protections; testing another browser requires a scope decision.
- Review Android dark/light, contrast, TalkBack labels, touch targets, font scaling, reduced motion, one-hand reach and performance/battery on typical hardware.

Do not set `PHYSICAL_VALIDATION_APPROVED=true` or promote to stable solely from CI. See [release configuration](releasing.md).
